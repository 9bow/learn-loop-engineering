## From Theory to Reality

The preceding chapters covered loop structure, patterns, and failure modes at a conceptual level. Section 12 is about practice. We dissect how two coding agents used by millions of people every day — Anthropic's Claude Code and OpenAI's Codex — actually implement their loops. These two systems embody different design philosophies, yet each had to solve the same core problems.

Recall Boris Cherny, the lead of Claude Code:

> "I no longer prompt Claude. I run loops and let it figure out what to do. My job is to write the loop."

That single sentence captures the philosophy of modern coding agents.

## Claude Code: Context, Action, and Evaluation

Claude Code's official guide describes gathering context, taking action, and evaluating results. These phases blend and repeat. The harness supplies tools, manages context, and applies permissions. A question can need only reading. A bug fix can need many edit-test cycles.

```text
User goal and constraints
        |
        v
Assemble context -> model selects an action
        ^                  |
        |                  v
Observe tool result <- authorize and execute tool
        |
        +-> model ends its turn or requests another action
```

### File-based instructions

`CLAUDE.md` stores project instructions. It is not a record of every completed action or a security boundary. Keep important rules there, and store task progress with links to the current files and evidence.

### Compaction and context lifetime

Claude Code clears old tool output and summarizes conversation history as needed. Current documentation supports configurable auto-compaction and explains that thresholds depend on the model and configuration. A fixed 92% threshold is not a general contract. Use `/context` to inspect the session and `/compact` to guide the summary.

### Subagents and shared resources

Subagents use separate context windows and return results to the caller. Context separation limits transcript growth. It does not itself isolate filesystem writes, network access, or credentials. Assign file ownership and enforce execution permissions separately.

## OpenAI Codex: Plan-Execute-Verify-Fix

The January 2026 Codex loop article describes repeated model inference and tool execution. The harness builds the prompt, sends it to the model, executes requested tools, and returns their results. A final assistant message ends that turn.

Plan-execute-evaluate-fix is a useful engineering pattern, not a mandatory four-state product machine. The model can revise the plan, investigate without editing, encounter a budget limit, or report a blocker. A final message alone does not prove that tests passed.

```text
Goal -> inspect repository -> plan when needed
     -> edit and run tools -> inspect actual results
     -> fix or report a blocker -> present evidence
```

### Historical training claims

The initial 2025 cloud product used codex-1. Treat that model name as release history, not the current product definition. Training a model to use tests does not replace a task-specific acceptance gate.

### Local and cloud execution

Codex CLI works on a local repository. Hosted cloud environments provide another execution surface. Their filesystem, networking, secrets, and approval policies differ. A container reduces impact but does not cancel authorized external API effects or prevent every escape.

Make sure that the requested checks actually ran. Separate task success from budget exhaustion, refusal, and infrastructure failure. Creating or submitting a pull request is a separate action governed by the user's request and permissions.

## Common Principles Across Both Systems

| Design concern | Practical contract |
|---|---|
| Completion | Separate model turn end from evidence of task success |
| Context | Preserve goals, current state, and source references across summaries |
| Isolation | Enforce filesystem, network, and credential boundaries |
| Evaluation | Run relevant tests and inspect their actual results |
| External actions | Apply authorization before the action, including publication |

These are design requirements for a reliable loop. They do not imply identical internals across products or releases. The next chapter examines SWE-agent's ACI choices.
