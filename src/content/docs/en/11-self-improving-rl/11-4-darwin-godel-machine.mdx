## What Is Self-Modification?

AlphaEvolve searches over algorithms. Darwin Gödel Machine (DGM) searches over the coding agent's own scaffold, the code that manages its tools and workflow. Its foundation model weights remain frozen in the reported experiments.

The paper reports an increase from 20.0% to 50.0% on its evaluated SWE-bench Verified subset of 200 tasks. It also reports 14.2% to 30.7% on the full Polyglot benchmark. Keep the task subset and evaluation setup with these numbers. They are not a full 500-task Verified leaderboard result.

DGM uses empirical coding results rather than formal proofs that each change is beneficial. Benchmark success does not prove safety outside the evaluated tasks.

## The DGM Self-Modification Loop

DGM keeps an archive of agent variants and their parent-child relationships. It samples a parent, asks that agent to modify its scaffold, and evaluates the new agent. A variant must compile and retain code-editing ability to enter the archive.

```text
Archive of agents and evaluation records
          |
          v
Select a parent using performance and exploration criteria
          |
          v
Parent proposes and implements a scaffold change
          |
          v
Evaluate the candidate in a controlled environment
          |
          v
Retain eligible variants and their lineage in the archive
          |
          +----> Sample another parent
```

Archive admission does not require every variant to beat its parent. Lower-scoring variants can become stepping stones to later improvements. A loop that discards every non-improving candidate describes greedy hill climbing, not the paper's open-ended search.

## What Gets Modified: Levels of the Scaffold

In DGM, what the agent modifies is the **scaffold code it uses to solve problems**. This spans several layers.

| Modification Layer | Examples |
|---|---|
| Tool interface | Timeout value for the `bash` tool, output parsing logic |
| Context management | Which files to read first, summarization strategy |
| Error handling | Retry logic for specific error patterns |
| Task decomposition | How to break large tasks into subtasks |
| Verification strategy | Which tests to run first after a code change |

The agent experiments with these layers, validates through the benchmark, and accumulates beneficial mutations. Over tens to hundreds of generations, a scaffold specialized for a particular benchmark evolves automatically.

## Comparison with AlphaEvolve

Both use an evolutionary loop, but DGM **evolves a different target**.

```text
┌────────────────────┬──────────────────────┬──────────────────────┐
│                    │    AlphaEvolve        │ Darwin Gödel Machine │
├────────────────────┼──────────────────────┼──────────────────────┤
│ Evolution target   │ Algorithm code        │ Agent scaffold code  │
│ Evaluation crit.   │ Math perf, throughput │ Coding benchmark %   │
│ Population struct  │ Explicit population   │ Version lineage      │
│ Mutation unit      │ Single algorithm      │ Agent components     │
│ Self-reference     │ None                  │ Yes (rewrites self)  │
└────────────────────┴──────────────────────┴──────────────────────┘
```

AlphaEvolve builds better tools (algorithms). DGM improves the **craftsman (agent) who uses the tools**.

## Safety Controls and Evaluation Limits

Sandboxing, human oversight, and traceable changes constrain the experiment. They are separate from the coding score. DGM does not supply a general safety guarantee or permission for arbitrary self-modification.

Keep evaluation code, credentials, and release permissions outside the mutable scaffold. Use held-out tasks and review changes that affect tool execution or policy. A higher benchmark score can conceal reward hacking, overfitting, or regressions outside the measured domain. Archive admission and production release require different gates.

## The Loop Engineer's Perspective

The most important insight DGM offers is that **the loop itself can become the object of improvement**. Throughout this course we have treated the loop as something the engineer designs. DGM points toward loops that design themselves.

Two practical takeaways emerge.

First, **meta-loop design**. Separate the inner loop (solving problems) from the outer loop (improving the scaffold), and define the outer loop's verification criterion clearly. That separation is the foundation for automated improvement.

Second, **the importance of the benchmark**. A self-modification loop depends entirely on the quality of its evaluation criterion. A poor benchmark sends the loop converging in the wrong direction. What you choose to measure determines where the loop goes.
