## Not Every Step Needs the Same Model

An agent loop mixes tasks of very different complexity: deep reasoning about the next action to take, extraction of tool call parameters, simple text parsing, summarization of tool results. Routing all of these through the most expensive frontier model is wasteful.

**Model routing** is the strategy of matching each task to the model tier that fits its complexity — reducing cost while preserving overall quality. Anthropic explicitly recommends task-complexity-based model selection in multi-agent systems.

## Model Tiers in an Agent Loop

```text
┌─────────────────────────────────────────────────────────────────┐
│              Model Tier Structure for an Agent Loop             │
├───────────────────────┬─────────────────────────────────────────┤
│  Tier                 │  Appropriate Tasks                      │
├───────────────────────┼─────────────────────────────────────────┤
│  Frontier (Opus-class)│  Task decomposition, complex reasoning  │
│                       │  orchestration decisions, ambiguous     │
│                       │  instruction interpretation, quality    │
│                       │  judgment                               │
├───────────────────────┼─────────────────────────────────────────┤
│  Mid (Sonnet-class)   │  Code generation, tool call sequencing  │
│                       │  structured output, multi-step reasoning│
├───────────────────────┼─────────────────────────────────────────┤
│  Light (Haiku-class)  │  Tool parameter extraction, text parsing│
│                       │  result summarization, simple           │
│                       │  classification, format conversion      │
└───────────────────────┴─────────────────────────────────────────┘
```

In the orchestrator pattern these tiers map cleanly to architectural roles. The **orchestrator** plans the overall task and distributes subtasks, so a frontier model is appropriate. **Workers** execute concrete subtasks they have been assigned, so a mid-tier model is often sufficient. **Inner-loop** steps — tool result parsing, simple format conversion — can be handled by a light model.

## RouteLLM: Data-Driven Routing

**RouteLLM**, developed by the LMSYS research team, is an LLM routing system in which a learned classifier decides whether each query should go to a strong model or a weak model. The 2024 experiments routed between GPT-4 Turbo and Mixtral 8x7B. They retained 95% of GPT-4 performance under the reported benchmark settings while reducing cost. This is a historical result, not a guarantee for newer models or multi-turn agents.

The core insight is that **the router itself is a lightweight classifier** — a small model or rule-based system that looks at a query and decides "does this need the strong model, or is the weak model sufficient?" Fallback can limit some routing errors. It does not undo incorrect tool actions, so evaluate routing quality and control side effects before execution.

Applied to an agent loop, a router at each iteration decides "can this step be handled by the light model?" and routes accordingly.

## A Practical Routing Implementation

This is application pseudocode. The adapter preserves full assistant content and normalizes tool calls. It returns tool results using the Anthropic message format.

The model IDs are examples from the October 23, 2026 catalog. They are not a universal ranking. The length heuristic needs task-specific evaluation.

```python
import json
from enum import Enum

class ModelTier(Enum):
    FRONTIER = "claude-opus-5-5"
    MID = "claude-sonnet-5-5"
    LIGHT = "claude-haiku-5-5"

def route_iteration(messages, iteration, has_tool_result):
    if iteration == 0:
        return ModelTier.FRONTIER
    content = messages[-1].get("content", "") if messages else ""
    text = content if isinstance(content, str) else json.dumps(content)
    if has_tool_result and len(text) < 500:
        return ModelTier.LIGHT
    if len(text) > 2000 or "plan" in text.lower():
        return ModelTier.FRONTIER
    return ModelTier.MID


def run_routed_loop(task: str, tools: list) -> str:
    messages = [{"role": "user", "content": task}]
    for iteration in range(20):
        content = messages[-1].get("content", "")
        has_tool_result = isinstance(content, list) and any(
            isinstance(block, dict) and block.get("type") == "tool_result"
            for block in content
        )
        tier = route_iteration(messages, iteration, has_tool_result)
        response = call_model(messages, model=tier.value, tools=tools)
        messages.append({"role": "assistant", "content": response.content})
        if response.stop_reason == "end_turn":
            return response.text
        if response.stop_reason != "tool_use" or not response.tool_calls:
            raise RuntimeError(f"Unexpected stop: {response.stop_reason}")
        results = []
        for call in response.tool_calls:
            try:
                result = str(execute_tool(call.name, call.input))
                is_error = False
            except (KeyError, TypeError, ValueError) as error:
                result, is_error = str(error), True
            results.append({"type": "tool_result", "tool_use_id": call.id,
                            "content": result, "is_error": is_error})
        messages.append({"role": "user", "content": results})
    raise RuntimeError("Iteration budget exhausted; task is incomplete")
```

## Risks and Mitigations

Routing has failure modes. Misrouting to a light model can degrade reasoning quality for that step, and this degradation can contaminate subsequent steps.

Choose routing rules from measured task quality, latency, and cost. A valid `end_turn` can be a final answer and does not require another tool call. Escalate when a result fails an independent outcome or schema test. Avoid repeating external actions when retrying with a different model.

Measure the share of simple steps and include routing, retries, cache behavior, and model-switching costs. A smaller model does not guarantee a lower cost per successful task.
