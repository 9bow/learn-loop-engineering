## 프레임워크를 선택하는 이유와 주의점

에이전트 프레임워크는 도구다. 도구가 좋으면 어려운 작업이 쉬워지지만, 잘못 선택하면 프레임워크 자체와 싸우는 데 시간을 낭비한다. Anthropic의 권고처럼 "가능하면 단순하게 시작하라"는 원칙은 프레임워크 선택에도 적용된다. 프레임워크 없이 직접 구현할 수 있는 수준의 루프에 무거운 프레임워크를 도입하면 추상화 레이어가 오히려 디버깅을 어렵게 만든다.

이 챕터에서는 현재 가장 많이 사용되는 다섯 가지 프레임워크를 설계 철학의 관점에서 비교한다.

## LangGraph: 상태 머신으로서의 에이전트

**핵심 패러다임**: 에이전트 루프를 **유향 그래프(directed graph)**로 모델링한다. 노드는 LLM 호출이나 도구 실행을 나타내고, 엣지는 상태 전이를 나타낸다. **조건부 엣지(conditional edge)**로 에이전트의 결정에 따라 다른 노드로 분기할 수 있다.

**상태 관리**: `TypedDict`로 정의된 공유 상태가 그래프 전체를 흐른다. 각 노드는 상태를 읽고 업데이트하는 순수 함수처럼 동작한다. 설정한 **체크포인터(checkpointer)**가 super-step 경계의 상태를 저장한다. 병렬 노드와 외부 부작용의 재실행 경계는 별도로 설계한다.

**인터럽트(interrupt)**: LangGraph는 그래프 실행을 특정 노드에서 일시 중단하고 인간의 승인을 받을 수 있는 `interrupt()` 메커니즘을 제공한다. 이것이 6-5 챕터에서 다룬 휴먼인더루프(human-in-the-loop) 패턴의 구체적 구현이다.

```text
┌─────────────────────────────────────────────────────────────┐
│           LangGraph 그래프 구조 예시                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  START ──→ [Plan] ──→ [Execute] ──→ [Verify]               │
│                            │              │                 │
│                            │         pass ▼    fail        │
│                            │       [Done]   ──→ [Retry]    │
│                            │                      │        │
│                            └──────────────────────┘        │
│                          (조건부 엣지: 재계획 또는 재시도)    │
└─────────────────────────────────────────────────────────────┘
```

**적합한 상황**: 복잡한 제어 흐름, 명확한 상태 전이, 체크포인트가 필요한 장기 실행 워크플로, 프로덕션 신뢰성이 중요한 시스템.

## OpenAI Agents SDK: 핸드오프 중심의 단순한 프리미티브

SDK는 핸드오프와 에이전트를 도구로 사용하는 매니저 방식을 모두 지원한다. 전문가가 대화를 이어받을지, 매니저에게 결과만 반환할지 선택한다.

`SQLiteSession` 같은 세션 저장소로 대화 기록을 유지할 수 있고, 인간 승인은 실행 중단과 재개 가능한 run state로 처리한다. 둘 다 외부 서비스 전체의 트랜잭션을 보장하는 기능은 아니다.

가드레일은 일반 코드나 다른 모델을 사용할 수 있다. 병렬 입력 가드레일이 끝나기 전에 에이전트가 도구를 실행할 수 있으므로 실행을 대기시켜야 한다면 차단 모드를 사용한다. 민감한 도구의 권한은 실행 경계에서 따로 강제한다.

## CrewAI: 역할 기반의 팀 협업

**핵심 패러다임**: 에이전트를 **역할(role)**과 **목표(goal)**, **배경(backstory)**을 가진 팀원으로 정의한다. 에이전트들이 **태스크(task)** 시퀀스를 통해 협력한다. 인간이 팀을 구성하는 방식을 LLM 에이전트로 모델링한다는 개념이 특징이다.

**실행 모드**: `sequential`(순차, 한 에이전트가 완료하면 다음 에이전트 시작)과 `hierarchical`(계층, 매니저 에이전트가 태스크를 할당)을 지원한다.

**적합한 상황**: 역할이 명확히 정의된 비즈니스 프로세스, 높은 수준의 추상화가 필요한 비개발자 친화적 설정, 팀 메타포가 도메인과 잘 맞는 경우.

## AutoGen: 대화 기반 멀티에이전트

AutoGen은 메시지 기반 협업을 학습하기 좋은 사례지만 API 세대를 구분해야 한다. `GroupChatManager` 중심 예제는 구세대 API의 설명이다. 이후 AgentChat은 이벤트 기반 Core와 별도 모델·실행 확장 위에서 동작한다.

2026년 10월 23일 확인한 Microsoft 저장소는 신규 프로젝트에 Microsoft Agent Framework를 안내하고 기존 사용자에게 마이그레이션 가이드를 제공한다. AutoGen은 기존 시스템·역사적 비교로 다룬다. 신규 배포는 예전 인기도가 아니라 후속 프레임워크의 릴리즈·마이그레이션 계약을 검토해 선택한다.

## smolagents: CodeAct와 경량화

**핵심 패러다임**: **CodeAct** — 에이전트가 도구를 JSON으로 호출하는 대신 **Python 코드를 직접 작성하고 실행**한다. 코드 자체가 액션이다. 이 접근법은 복잡한 도구 체이닝을 코드 한 줄로 표현할 수 있다는 장점이 있다.

Hugging Face가 개발했으며, 경량화와 최소 의존성을 설계 철학으로 삼는다. 로컬 모델과 오픈소스 모델 지원에 강점이 있다.

**적합한 상황**: 코드 실행 에이전트, 오픈소스·로컬 모델 활용, 최소 의존성이 중요한 환경, 연구 프로토타이핑.

## 프레임워크 비교표

근거 없는 성숙도 등급 대신 실제 메커니즘을 비교한다. 아래는 2026년 10월 23일 확인 기준 기능 안내다.

| 프레임워크 | 제어 모델 | 영속화·검토 |
|---|---|---|
| LangGraph | 명시적 상태 그래프 | 설정한 체크포인터와 `interrupt()` |
| Agents SDK | 핸드오프 또는 에이전트 도구 | 세션 저장소와 승인 중단 |
| CrewAI | Crew와 이벤트 기반 Flow | Flow 상태와 설정한 영속화 |
| AutoGen | AgentChat과 이벤트 기반 Core | 기존 시스템 유지·이관 검토 |
| smolagents | CodeAgent 또는 도구 호출 | 실행기 격리와 애플리케이션 상태 정책 |

대화 메모리·프로세스 장애 복구·외부 행동 중복 방지는 별도 요구사항이다. 선택한 저장소에서 각각 테스트한다. 인메모리 saver만으로 프로세스 종료 후 데이터를 복구할 수는 없다.

## 선택 기준

어떤 프레임워크도 모든 상황에 최적이지 않다. 다음 질문이 선택을 안내한다.

**복잡한 분기 로직이 필요한가?** → LangGraph. 조건부 엣지와 명시적 상태 그래프가 복잡한 제어 흐름을 명확하게 표현한다.

**핸드오프 기반의 전문화가 핵심인가?** → Agents SDK. 미니멀한 프리미티브로 빠르게 시작할 수 있다.

**도메인 전문가가 에이전트를 구성해야 하는가?** → CrewAI. 역할과 목표로 구성하는 인터페이스가 비개발자에게 친숙하다.

**에이전트 간 대화를 자연어로 관찰해야 하는가?** → 메시지 기반 협업과 로그를 검토한다. 신규 Microsoft 기반 시스템이라면 Microsoft Agent Framework도 비교한다.

**오픈소스 모델을 쓰거나 코드 실행이 핵심인가?** → smolagents. CodeAct 패러다임과 경량 설계가 강점이다.

**검증된 체크포인트와 롤백이 프로덕션에 필요한가?** → 저장소 영속성·재실행 경계·부작용 중복 방지를 실제 장애 실험으로 비교한다.

## 섹션 마무리

이 섹션에서는 멀티에이전트 시스템이 단일 에이전트의 한계를 어떻게 넘어서는지, 그리고 그 넘어섬이 새로운 문제들 — 시간 지평선, 오류 복리, 멜트다운 — 을 어떻게 만들어내는지를 살펴봤다. 프레임워크는 이 문제들에 대한 각자의 답을 가지고 있으며, 시스템의 요구사항에 따라 올바른 도구를 선택하는 것이 루프 엔지니어의 핵심 역량이다.
