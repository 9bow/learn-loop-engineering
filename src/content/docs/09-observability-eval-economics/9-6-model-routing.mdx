## 모든 스텝에 동일한 모델을 쓸 필요가 없다

에이전트 루프에는 다양한 수준의 작업이 섞여 있다. 다음 행동을 결정하기 위한 심층 추론, 도구 호출 파라미터 추출, 단순 텍스트 파싱, 도구 결과 요약 — 이 모든 작업을 가장 비싸고 가장 강력한 프런티어 모델에 맡기는 것은 낭비다.

**모델 라우팅(model routing)**은 각 작업의 복잡도에 맞는 모델을 선택해 비용을 줄이면서 전체 성능을 유지하는 전략이다. Anthropic은 에이전트 시스템에서 작업 복잡도에 따른 모델 선택을 명시적으로 권장한다.

## 에이전트 루프의 모델 계층

```text
┌─────────────────────────────────────────────────────────────────┐
│                 에이전트 루프의 모델 계층 구조                     │
├───────────────────────┬─────────────────────────────────────────┤
│  계층                 │  적합한 작업                             │
├───────────────────────┼─────────────────────────────────────────┤
│  프런티어 (Opus 계열) │  작업 분해, 복잡 추론, 오케스트레이션 결정  │
│                       │  모호한 지시 해석, 품질 판단              │
├───────────────────────┼─────────────────────────────────────────┤
│  중간 (Sonnet 계열)   │  코드 생성, 도구 호출 시퀀스 계획          │
│                       │  구조화 출력 생성, 다단계 추론            │
├───────────────────────┼─────────────────────────────────────────┤
│  경량 (Haiku 계열)    │  도구 파라미터 추출, 텍스트 파싱           │
│                       │  결과 요약, 단순 분류, 포맷 변환          │
└───────────────────────┴─────────────────────────────────────────┘
```

오케스트레이터 패턴에서 이 계층은 명확하게 분리된다. **오케스트레이터(orchestrator)**는 전체 작업 계획을 세우고 서브태스크를 분배하므로 프런티어 모델이 적합하다. **워커(worker)**는 분배받은 구체적인 서브태스크를 수행하므로 중간 모델을 쓸 수 있다. **내부 루프(inner loop)** — 도구 결과 파싱, 단순 포맷 변환 등 — 은 경량 모델이 충분히 처리한다.

## RouteLLM: 데이터 기반 라우팅

**RouteLLM**은 LMSYS 연구팀이 개발한 LLM 라우팅 시스템으로, 쿼리별로 강력한 모델과 약한 모델 중 어느 것으로 라우팅할지를 학습된 라우터가 결정한다. 2024년 실험은 GPT-4 Turbo와 Mixtral 8x7B를 라우팅했다. 보고된 벤치마크 조건에서 GPT-4 성능의 95%를 유지하면서 비용을 줄였다. 이는 당시의 결과이며 최신 모델이나 다중 턴 에이전트에서도 같은 효과를 보장하지 않는다.

RouteLLM 접근법의 핵심은 **라우터 자체가 경량 분류기**라는 점이다. 쿼리를 보고 "이 쿼리는 강력한 모델이 필요한가, 약한 모델로 충분한가"를 판단하는 작은 모델이나 규칙 기반 시스템이다. 폴백은 일부 오류의 영향을 줄일 수 있지만 이미 실행한 외부 행동을 되돌리지는 못한다. 라우팅 품질과 상태 변경 권한을 실행 전에 함께 검증한다.

에이전트 루프에서 이 아이디어를 적용하면, 각 이터레이션에서 라우터가 "이 단계는 경량 모델로 처리 가능한가"를 판단해 비용을 줄인다.

## 실용적 라우팅 구현

아래 코드는 애플리케이션 어댑터를 사용하는 의사 코드다. 어댑터는 assistant 응답 전체와 정규화한 도구 호출을 보존하고, 도구 결과는 Anthropic 메시지 형식으로 반환한다.

모델 ID는 2026년 10월 23일 공식 목록의 예시이며 모든 작업의 성능 순위를 뜻하지 않는다. 글자 수를 사용하는 라우팅 규칙은 학습용 휴리스틱으로, 실제 작업에서 별도로 평가해야 한다.

```python
import json
from enum import Enum

class ModelTier(Enum):
    FRONTIER = "claude-opus-5-5"
    MID = "claude-sonnet-5-5"
    LIGHT = "claude-haiku-5-5"

def route_iteration(messages, iteration, has_tool_result):
    if iteration == 0:
        return ModelTier.FRONTIER
    content = messages[-1].get("content", "") if messages else ""
    text = content if isinstance(content, str) else json.dumps(content)
    if has_tool_result and len(text) < 500:
        return ModelTier.LIGHT
    if len(text) > 2000 or "plan" in text.lower():
        return ModelTier.FRONTIER
    return ModelTier.MID


def run_routed_loop(task: str, tools: list) -> str:
    messages = [{"role": "user", "content": task}]
    for iteration in range(20):
        content = messages[-1].get("content", "")
        has_tool_result = isinstance(content, list) and any(
            isinstance(block, dict) and block.get("type") == "tool_result"
            for block in content
        )
        tier = route_iteration(messages, iteration, has_tool_result)
        response = call_model(messages, model=tier.value, tools=tools)
        messages.append({"role": "assistant", "content": response.content})
        if response.stop_reason == "end_turn":
            return response.text
        if response.stop_reason != "tool_use" or not response.tool_calls:
            raise RuntimeError(f"Unexpected stop: {response.stop_reason}")
        results = []
        for call in response.tool_calls:
            try:
                result = str(execute_tool(call.name, call.input))
                is_error = False
            except (KeyError, TypeError, ValueError) as error:
                result, is_error = str(error), True
            results.append({"type": "tool_result", "tool_use_id": call.id,
                            "content": result, "is_error": is_error})
        messages.append({"role": "user", "content": results})
    raise RuntimeError("Iteration budget exhausted; task is incomplete")
```

## 라우팅의 리스크와 완화

라우팅에는 실패 모드가 있다. 경량 모델로 잘못 라우팅했을 때 추론 품질이 떨어질 수 있고, 이것이 이후 스텝을 오염시킬 수 있다.

실제 작업의 품질·지연·비용을 측정해 라우팅 규칙을 정한다. 올바른 최종 답변은 `end_turn`으로 끝날 수 있으므로 도구 호출이 없다는 이유만으로 실패로 판정하지 않는다. 독립적인 결과 검증이나 스키마 검사에 실패하면 상위 모델로 넘기되, 이미 실행한 외부 행동을 중복하지 않는다.

단순 단계의 실제 비중과 라우터·재시도·캐시·모델 전환 비용을 함께 측정한다. 작은 모델을 선택하는 것만으로 성공한 작업당 비용이 낮아지는 것은 아니다.

## 섹션 마무리: 관찰·평가·경제학의 삼각형

이 섹션에서 다룬 세 가지 주제 — 트레이싱(9-1), 평가(9-2~9-3), 경제학(9-4~9-6) — 은 사실 하나의 시스템으로 연결된다. 트레이싱이 없으면 비용 어디서 나오는지 알 수 없다. 평가가 없으면 모델을 다운그레이드해도 품질이 유지되는지 알 수 없다. 경제학을 모르면 트레이싱과 평가 인프라에 얼마를 써야 할지 결정할 수 없다. 이 삼각형이 프로덕션 에이전트 시스템의 운영 기반이다.
